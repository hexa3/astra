# Astra engineering decisions

## 1. Build an experience on Electron, not a new engine — 2026-09-05

Astra uses Electron 44, Chromium, TypeScript, Svelte 5, Vite, electron-builder and better-sqlite3. A fresh, small experience layer lets contributors replace browser features without maintaining a Chromium fork; a fork would offer deeper extension and browser-service compatibility but greatly exceed this mission's maintenance budget. Electron does not provide all Chrome extension APIs or the Chrome Web Store installation flow: compatibility must be tested and described honestly. Remote sites live in sandboxed WebContentsViews, never the privileged UI. The main process owns a single typed state and validates the UI's narrow IPC commands. Reference: https://www.electronjs.org/docs/latest/tutorial/security and https://www.electronjs.org/docs/latest/api/web-contents-view.

## 2. Encrypt application records; keep website storage ephemeral — 2026-09-05

History, bookmarks and saved sessions are authenticated encrypted payloads in SQLite using a random AES-256-GCM key wrapped by the operating-system key store through Electron safeStorage. No URL or title becomes a plaintext index. On Linux, the basic_text backend is explicitly rejected. When a secure key store is unavailable, the browser works in memory and clearly reports that persistence is unavailable; a passphrase unlock path will follow. Chromium sessions use nonpersistent partitions with disk cache disabled, so website cookies and storage do not survive quitting. This privacy/compatibility tradeoff is disclosed in the UI and README. We will not claim that normal Chromium profile files are fully encrypted. Reference: https://www.electronjs.org/docs/latest/api/safe-storage.

## 3. Default privacy before feature breadth — 2026-09-05

Application UI has a network-denying CSP and bundled fonts, no telemetry, updater, analytics or crash uploader. Page sessions deny sensitive permissions initially and intercept known tracker hosts using a bundled, reviewable seed list. Third-party network cookies are stripped using registrable-domain comparisons rather than unsafe hostname suffix guesses; additional document-cookie verification is part of the first milestone. We disable spellcheck downloads and Chromium background networking where exposed. A small seed blocklist is basic protection, not a claim of comprehensive ad blocking. Request counters must count actual events.

## 4. Portable passphrase vault when keychain access is unavailable — 2026-09-05

The first launch on this Linux desktop confirmed that safeStorage has no secure backend. The fallback is an explicit passphrase vault, not a plaintext key on disk. A 32-byte random salt and scrypt (N=32768, r=8, p=1) derive a wrapping key; AES-256-GCM wraps the random database key with version-specific associated data. Every record uses a fresh nonce and its record ID as associated data. The passphrase is never stored, and derived key buffers are cleared. Unlock merges records created during this session with saved records and restores tabs lazily. Corrupt or missing key files must not cause a new key to overwrite an existing database. Browser encryption protects stored records from someone without the key, not malware running as the unlocked user; downloads remain ordinary files the user explicitly saves.

## 5. Package early and keep publishing separate from the application — 2026-09-05

The first Linux artifact is built before expanding the feature set so packaging errors surface while the system is small. AppImage and Debian packages share the same Electron build, and a separate smoke script verifies the packaged executable using an isolated configuration directory. The source repository is public at https://github.com/hexa3/astra under the already authenticated account. electron-builder's implicit publishing metadata is disabled (`publish: null`); releases are deliberate development actions through GitHub, and no updater is included in Astra. On this Arch host, a user-local FPM using the system Ruby replaces electron-builder's bundled Ruby because the latter requires missing libcrypt.so.1. No system library downgrade or privileged installation is needed.

## 6. Hibernate conservatively; report process memory honestly — 2026-09-05

The default keeps six background page views live, configurable from zero to 32. Least-recently-used pages beyond that limit are destroyed and restored on selection using Chromium's navigation history and scroll position; website session cookies remain in the shared in-memory session. We inspect all frames for edited forms and editable content, retain audible pages, and honor beforeunload protection so memory savings do not silently discard detected work. This means protected pages can exceed the configured target. Inspection failures keep the page awake. Hibernation reloads the page and is not a serialized JavaScript heap or an instantaneous offline restore. The resource panel samples Electron's real main-renderer process working set every five seconds and explicitly labels possible process sharing; it does not invent a per-tab total that omits or double-counts subprocesses.

## 7. One writer per profile and explicit page-close consent — 2026-09-05

Electron's single-instance lock is acquired after selecting the profile directory, preventing two application processes from overwriting the same encrypted record sets. A second launch forwards explicit HTTP/HTTPS arguments to the running instance; it does not register Astra as the default browser without a user action. User-requested tab/window closure runs page beforeunload handlers and presents a native Stay/Leave choice when needed. Automatic hibernation has a separate path that honors the page's request to remain open without showing a surprise dialog. Window closure retains saved tab records; if a later page cancels quitting, earlier closed page views can be restored from their URLs. Tabs in a close operation are excluded from hibernation to avoid competing lifecycle operations.

## 8. Workspaces isolate website sessions, with shared local libraries — 2026-09-05

Workspaces own tab membership and independent in-memory Electron sessions, separating cookies and website storage for work/personal/research identities. Every session installs the same privacy and permission handlers. The original Personal workspace retains the initial partition for profile compatibility; named workspaces use generated IDs, independent of their renameable labels. Bookmarks/history remain a shared local library, disclosed in workspace settings. Encrypted records store names, IDs and tab membership; old sessions migrate into the default workspace. Restored tabs stay asleep until selected, duplicate URLs remain valid distinct tabs, and restoring no longer silently truncates sessions at 50 pages. Ctrl+Tab stays within the current workspace; Ctrl/Cmd+Alt+Left/Right and number keys switch workspaces.

## 9. Exercise the sandboxed application in disposable CI desktops — 2026-09-05

GitHub Actions runs the locked Node 24 dependency install, production build, unit tests, real Electron browser tests, native unload tests and production dependency audit on Ubuntu 24.04 under Xvfb. Actions are pinned to verified upstream commit hashes and receive read-only repository permission. New pushes cancel older runs for the same branch. The disposable runner permits unprivileged user namespaces so Chromium's sandbox can operate; tests never use `--no-sandbox`, and that runner-only sysctl is not an application or installer change. Failure traces are retained for seven days. Native platform packaging and macOS/Windows execution will receive their own coverage instead of being inferred from a Linux pass.

## 10. A local command bar above native page views — 2026-09-05

The command bar searches the main process's existing snapshot: tabs across all workspaces, workspace names, bookmarks, deduplicated history, and implemented browser actions. Ranking is a small accent-insensitive fuzzy function with deterministic priorities; typing never contacts a suggestion service. Explicit submission can navigate or search using the same safe address resolver as the address bar. A native modal dialog uses a combobox/listbox interaction, arrow-key selection and an explicit two-control Tab cycle, since testing exposed a Chromium focus escape at the dialog boundary. Page views are temporarily hidden while the command bar is open so native surface ordering cannot cover trusted controls. Results dispatch the same validated commands as other browser UI; there is no separate privileged execution channel.

## 11. Identify the committed page, not an uncommitted destination — 2026-09-05

Address submission must not relabel an existing document before Chromium commits navigation: a stopped request, a download, HTTP 204 or a page's Stay choice can leave the previous document alive. The address resets to the committed URL when submitted and follows Chromium's committed navigation events, with a final reconciliation when loading stops. Failed destinations appear only with the native page hidden behind Astra's error screen, and retry explicitly loads that destination. An empty address submission is a no-op. The same Stay/Leave confirmation handles ordinary navigation and explicit closure, while automatic hibernation suppresses prompts and honors the page's protection. Reference: https://www.electronjs.org/docs/latest/api/web-contents#event-will-prevent-unload.

## 12. One tab order and one layout contract for both browser surfaces — 2026-09-05

Drag-and-drop and Alt+Shift+arrow reordering dispatch the same validated workspace-local operation; other workspace positions and every tab's identity remain unchanged. The encrypted saved session is the order record, with no parallel renderer-only ordering state. The extracted tab list uses manual keyboard activation, roving focus and spoken position announcements. Sidebar collapse retains a 56-pixel labeled icon/number rail rather than removing access to tabs and libraries. A shared layout module supplies both the Svelte grid width and native page bounds, avoiding overlapping trusted chrome when the width changes. Collapse is an encrypted preference, also available from Ctrl/Cmd+B and local command search. Restart tests caught and fixed the creation-time default overwriting an in-memory collapsed preference.

## 13. Split existing tabs without duplicating their state — 2026-09-06

Split view places two existing native page views from one workspace side by side, separated by one hairline. The pair retains fixed left/right identities as focus changes; the address and navigation controls always follow the focused page. Both visible pages are exempt from background hibernation, and browser panels hide both surfaces. Users can select a partner from local command search, toggle the pair with Ctrl/Cmd+Shift+S, or focus either pane through labeled buttons. This first implementation ends the split on opening/selecting a tab outside the pair, closing a member, or a member's navigation/process failure; it does not pretend to serialize split layout across restart or provide resizing. The underlying tabs and their records remain intact. Integration tests verify two actual native views, URL routing, stable positions, collapse alignment, panel isolation and command-based restoration.

## 14. Verify each desktop platform in its native runner — 2026-09-06

Windows x64, macOS arm64 and macOS x64 receive separate native source tests, electron-builder packages and packaged browsing smoke checks. Test-only development profiles bypass OS keychain access to exercise passphrase persistence consistently; packaged builds ignore that environment hook. A user-facing `--astra-profile=/absolute/path` option isolates a full profile without changing encryption policy and supplies disposable directories to packaged checks on every OS. CI receives read-only repository permissions and uploads artifacts only after runtime checks. Windows packages have no publisher certificate; macOS uses ad-hoc signing for executable integrity, not Developer ID verification or notarization. Neither is represented as a trusted signed release. This avoids treating Linux packaging or cross-compilation as evidence of native runtime compatibility.

## 15. Load reviewed MV3 extensions in disposable sessions — 2026-09-09

Unpacked Manifest V3 extensions are selected through a native directory dialog and loaded only after Astra displays their named permissions, optional permissions, host patterns and content-script matches for explicit approval. Registrations are stored inside the encrypted vault; a changed permission set disables the extension until it is removed and reviewed again. Extension-capable Chromium sessions require a filesystem path, so Astra places them in Linux RAM-backed storage when available and the operating-system temporary directory elsewhere, removes them on orderly exit, and does not claim extension data is encrypted or crash-proof. Enabling or disabling reloads live pages because Chromium only injects declarative content scripts during navigation. Chrome Web Store installation is not claimed: Electron supports only a subset of Chrome extension APIs, and Astra exposes failures instead of implying universal compatibility.

## 16. Scope site customizations to the active hostname — 2026-09-09

Boosts are exact-hostname CSS and JavaScript records stored with the encrypted browser vault and injected only after an HTTP(S) document finishes loading. The main process independently derives the active document hostname and rejects renderer commands naming any other domain; source fields are each capped at 100 KB. CSS uses Chromium's user origin, while JavaScript executes in the remote page's sandboxed main world so it can intentionally modify that site but cannot reach Node, the Astra bridge or trusted chrome. Saving, disabling or removing reloads the page because arbitrary page scripts cannot be reversed reliably. This is a power-user feature: the UI plainly describes its authority and surfaces execution errors instead of pretending user code is harmless.

## 17. Start AI with a replaceable, deterministic local provider — 2026-09-09

The optional AI surface is a dismissible right sidebar backed by a small `ModelProvider` contract rather than vendor-specific UI or state. Version 1 ships a deterministic extractive provider: the main process obtains at most 200,000 characters of rendered page text from the sandboxed document, ranks sentences locally, and returns a summary or question-relevant passages without any network call, model download, API key or telemetry. Results are explicitly described as extractive and fallible. Native page bounds reserve the sidebar width so trusted controls never cover content, and requests are rejected if navigation changes during extraction. Future local or remote providers can implement the same contract; any remote provider must add per-request disclosure and consent before it can ship.

## 18. Drive Peek from Chromium's real hover target — 2026-09-09

Peek listens to the remote `WebContents` target-URL event rather than injecting permanent hover listeners into arbitrary sites. Holding Alt over a validated HTTP(S) link starts a 350 ms intent delay and then opens that address in a separate sandboxed `WebContentsView`, inset within the current page bounds and sharing the active workspace session. Releasing Alt, leaving the link, pressing Escape or changing tabs destroys the preview; a trusted toolbar action can promote its committed URL to a normal tab. The preview rejects privileged navigation and popup creation through the same narrow URL policy. Preview requests are not attributed to the underlying tab's counter because doing so would misrepresent which document initiated them.

## 19. Persist one validated user accent — 2026-09-09

Astra retains the strict monochrome-plus-one-accent system while allowing the user to recolor that single functional token from the resource panel. The IPC boundary accepts only six-digit hexadecimal colors, normalizes case, and stores the choice inside the same encrypted vault as other browser preferences. The accent continues to serve focus, active-state and critical-error roles rather than decorative backgrounds. Native color input labeling, explicit textarea focus rings, reduced-motion handling and forced-color focus styles keep the customization from weakening keyboard or high-contrast accessibility.

## 20. Call 1.0 a complete product slice, not universal compatibility — 2026-09-09

Version 1.0 denotes the six user outcomes in the build directive and a packaged, tested browser—not completion of an evergreen browser ecosystem. The release includes explicit macOS/Windows/Linux build commands and native-runner packaging checks, but unsigned/unnotarized binaries remain plainly labeled. It names unpacked MV3 support rather than claiming Chrome Web Store parity, a small local tracker baseline rather than comprehensive blocking, automated accessibility coverage rather than manual certification, and extractive local assistance rather than autonomous agents. Shipping these constraints in the README and release notes protects the project's defining transparency better than inflating the feature list.

## 21. Release Windows extension files after the browser exits — 2026-09-09

Chromium's extension service worker can retain Windows file handles while Electron is already inside its synchronous `will-quit` event. Recursively deleting the disposable extension profile there can stall an otherwise clean shutdown. On Windows, Astra now starts a detached Electron-in-Node-mode cleanup helper with the exact application-generated temporary path; it retries removal after the parent releases those handles and has no browser privileges or network work. Linux and macOS retain direct synchronous removal. This is preferable to preserving extension state on disk or blocking browser shutdown, and the native MV3 process test covers the affected lifecycle boundary.

## 22. Retrospective: deepen verified foundations before broadening 1.0 — 2026-09-09

The mission delivered its six required user outcomes and the distinctive local-first product slice, but deliberately cut one-click Chrome Web Store installation, broad Chrome-extension API parity, remote/generative or form-acting AI, persisted resizable splits, a full maintained filter-list engine, cloud sync and commercial code signing. Each would require an ecosystem, trust surface or external credential that cannot be implemented honestly as a rushed toggle. Version 2 should first add signed release infrastructure and updater transparency, manual assistive-technology certification, crash-recovery tests and maintained privacy lists; then pursue a permission-audited extension catalog, persistent split layouts and opt-in provider plugins with visible per-request consent. The architecture keeps those surfaces replaceable, but 1.0 remains useful without them.

## 23. Use MPL 2.0 file-level copyleft for Astra-owned source — 2026-09-10

All repository commits before relicensing have the same recorded author and copyright holder, so Astra can relicense its own MIT source without purporting to revoke rights already granted for prior copies. Version 2 uses the unmodified Mozilla Public License 2.0 with SPDX notices on source files. MPL requires distributed modifications to covered files to remain available in source form while still permitting separate files in a Larger Work under other terms; therefore it guarantees the continued openness of Astra-derived covered files but is not described as project-wide GPL-style copyleft. Third-party dependencies and Doto retain their own licenses. This precise scope follows Mozilla's official MPL FAQ and Sections 3.1–3.3 of the license.

## 24. Bootstrap a public council without inventing a legal foundation — 2026-09-10

Astra presently has one recorded maintainer and no incorporated foundation, so governance names that fact instead of implying independent legal custody already exists. A public RFC and roll-call process governs architecture, policy, funding, and protected privacy commitments immediately; contribution-based eligibility automatically ends the bootstrap once three independent maintainers serve, after which employer concentration is capped. Public nomination forms, durable proposal/vote records, conflict recusals, a treasury ledger, appeal rules, and heightened thresholds turn the charter into an actionable process. MPL remains the legal backstop if future governors change policy; a governance document cannot truthfully promise that no future supermajority will ever amend itself.

## 25. Keep funding intake closed until custody is publicly accountable — 2026-09-10

No foundation, fiscal host, project bank account, or active donation processor exists, so Astra cannot honestly advertise a donation link or let one maintainer's personal account masquerade as a community treasury. The permitted paths are named now—unrestricted Community Fund donations, public-interest grants, and optional enterprise support—and issue forms make proposals actionable. Protected review must approve the legal recipient, material terms, conflicts, custody, and reporting before money moves; an append-only public ledger begins at zero. Search placement, ads, behavioral data, closed features, paid governance, and privacy concessions are excluded. Enterprise payments purchase disclosed services around the same open software, not product control.

## 26. Add a canonical runnable artifact before claiming installer reproducibility — 2026-09-10

Electron-builder's AppImage, Debian, NSIS, DMG, and ZIP outputs include platform tooling, signing envelopes, filesystem metadata, or timestamps that are not all controlled consistently across hosts. Astra therefore adds a Linux x64 release artifact whose complete Electron runtime and packaged application tree are canonicalized with GNU tar: sorted paths, a commit-derived `SOURCE_DATE_EPOCH`, numeric root ownership, GNU archive format, and timestamp-free gzip. The build runs inside an exact Node/Debian image digest with lockfile-verified npm inputs and Electron's checksummed runtime. The extracted artifact is a real runnable browser, not a source bundle. Native installers remain tested distribution conveniences and will not be described as byte-identical until each format independently proves it.

## 27. Version the shell boundary at the smallest privileged bridge — 2026-09-10

The stable core boundary is the context-isolated preload contract, not a direct JavaScript import into privileged browser state. Shells receive a read-only API version, capability discovery, immutable command vocabulary, snapshots, and state/shortcut subscriptions; commands still pass runtime validation and an exact trusted-frame authorization check in the main process. IPC channel names carry the major API version and exist in one protocol module. Architecture tests reject renderer imports from core implementation or Electron main-process modules. Pure layout/search helpers may remain shared libraries because they convey no authority or mutable core state. This preserves a narrow audited privilege boundary while allowing shells to compile and ship independently against `src/core/api.ts`.

## 28. Let shells declare geometry without granting arbitrary shell loading — 2026-09-10

Electron page views are native surfaces, so a core that hardcodes the default sidebar dimensions is not actually shell-independent. API 2.0 therefore accepts a bounded, process-local `configure-shell` inset command and calculates page, split, and Peek bounds from it. The minimal reference uses a single 52-pixel top bar and omits the default shell's sidebar, command palette, panels, AI UI, and font. Shell documents remain compile-time packaged and allowlisted: accepting an arbitrary local HTML path would give unreviewed code the trusted command bridge. A third-party shell replaces a build entry or proposes an audited slot without changing privileged core implementation.

## 29. Separate reviewable configuration from private browsing records — 2026-09-10

TOML under `$XDG_CONFIG_HOME/astra` or `~/.config/astra` is authoritative for non-secret settings, extension declarations and their reviewed manifest access, workspace structure, and explicit named startup sessions. Encrypted storage remains authoritative for history, bookmarks, live crash-recovery URLs, Boost source, and keys; moving those into dotfiles would regress the at-rest privacy baseline. Startup-session URLs reject credentials, queries, and fragments so generated config is safe to commit, while home-relative extension paths use the literal `$HOME` token rather than embedding a username. Files are written atomically with user-only permissions. Invalid user edits produce warnings and a safe in-memory fallback but are never silently overwritten.

## 30. Keep the CLI offline and share its validators with the browser — 2026-09-10

`astractl` is a bundled Node entry point over the same TOML store and Manifest V3 inspection code used by the browser. It performs no IPC, network request, browser automation, credential access, or vault decryption. Commands are non-interactive for reliable scripts: an extension install is itself the explicit enable action and prints the manifest's requested browser/site access; workspace exports go to stdout rather than choosing a destination on the user's behalf. Browser and CLI changes take effect across restart, with documented single-writer operation rather than a hidden background daemon. This keeps dotfiles usable on headless systems while leaving live private state behind the encrypted browser boundary.

## 31. Authenticate sync without giving the server the content key — 2026-09-10

Identity-free sync uses a user passphrase plus a random 32-byte Realm rather than an email, Astra account, OAuth provider, or organization server. Scrypt derives a master key; domain-separated HKDF outputs produce independent authentication and AES-256-GCM content keys. The reference server hashes the presented authentication key into its storage namespace but cannot use it to derive the content key. Device/version/sequence fields are authenticated context, uploads must increase their per-device sequence, and actual server-file scans prove URLs, names, passphrases and keys are absent. The first protocol deliberately chooses a small opaque-blob server over server-side merging: a compromised host can inspect metadata, deny service or replay old valid bytes, but cannot decrypt or undetectably edit records. Sync is explicit rather than periodic so configuration alone never creates background traffic.

## 32. Sync configuration stores pairing metadata, never key material — 2026-09-10

The browser writes only endpoint, random Realm, local device label, and a passphrase verifier to `sync.toml`. Authentication/content keys and the passphrase remain process-memory values derived for an explicit operation and are never persisted in dotfiles. The verifier catches accidental wrong-passphrase uploads, but a copied verifier permits offline guesses; users are therefore told to use a high-entropy passphrase. Manual sync is honest about its current last-writer-wins snapshot merge and avoids an undisclosed background connection.

## 33. Browser features do not become Astra web APIs — 2026-09-10

Boosts, resource reporting, local AI, Peek, Core API IPC, and sync are browser-chrome or service surfaces. None requires a website-visible primitive, so none justifies a W3C/WHATWG proposal today. Tabs and Peek share one exported web-preferences policy with no preload, and structural tests reject alternate construction or context-bridge exposure. The machine-readable inventory is mandatory for future custom surfaces. If a genuinely novel website-facing primitive becomes necessary, Astra will publish interoperability, privacy, threat and tentative specification work before enabling it by default rather than shipping a vendor-only API.
